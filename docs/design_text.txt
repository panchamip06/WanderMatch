2. Problem Understanding
The problem behind the product
Group trip planning breaks down when one or two people disagree, nobody wants to block the group, and the
disagreement is either steamrolled or lost in group-chat back-and-forth.
Existing shared-itinerary tools solve collaborative editing, but not the harder question: when preferences conflict,
who decides, how, and on what basis?
WanderMatch combines a live shared itinerary, structured proposal-and-vote flow, and an AI layer that reads the
reasons behind objections — not just the yes/no tally — to produce common ground or, when preferences are
genuinely incompatible, parallel branches.
The design goal is a system that never silently overrides anyone, never gets permanently stuck, and never treats an
LLM suggestion as authoritative: the admin or a unanimous group agreement can always override it.
3. Scope
What is built — and what is deliberately left out
BUILD: trip creation/invites/auth; live PostgreSQL itinerary with FastAPI WebSockets; proposal + Yes/No/Abstain
voting; Mode A Admin-Led consensus; Mode NA No-Admin common-ground + branching; recursive multi-way
branches; mandatory Trip Chat; solo-to-group and solo-to-guide matching; optional face registration; Cloudinary
trip photos + DeepFace tagging.
LEFT OUT: admin-inactivity fallback; live self-hosted LLM serving; live face recognition during judging (fixed demo
photos are pre-processed); AI follow-up questioning; live translation of user-generated content; deep AI-training
detail.
4. User Journey
How a traveller moves through WanderMatch
Sign-up → Firebase Auth → age, languages and travel interests → optional three-photo face registration → create/join
a trip and choose Admin-Led or No-Admin mode.
Trip Home shows day-by-day slots with statuses: Empty / Proposing / Voting / Common-Ground Round n /
Branching / Confirmed.
Slot Detail exposes every proposal, live tally and every stated No-reason. Members submit proposals, vote Yes, or
vote No with a mandatory typed reason.
If disagreement triggers AI, the AI candidate appears alongside the original. If branching occurs, members see their
branch preview and can Confirm or Request Modification.
Solo travellers get ranked group matches with reasons, or guide matches using language, specialisation, price and
rating. Trip Photos offers shared gallery + optional personal face-tagged albums.

5. Architecture
Simple single-orchestrator design

Registration

broadcast manager
PostgreSQL PS-11 schema + additive tables; system of record
Hosted LLM API Consensus generation and branch synthesis
Cloudinary Photo storage, thumbnails and delivery
Face service Python + DeepFace / ArcFace
Deployment Vercel/Render + managed PostgreSQL
React never talks directly to PostgreSQL, the LLM API, Cloudinary or the face service. Every request and state-
changing broadcast passes through FastAPI. WebSockets provide one live channel per trip. A Redis-backed
connection manager can be swapped in later for multi-instance scaling.
5A. Consensus & Conflict Resolution — Detailed Flow
The timer only exists once there's a No. There is no fixed voting window starting at proposal creation. The 10-minute
response window starts when the FIRST No lands on a slot.
Mode A — Admin-Led
# Step Behaviour
1 Admin creates base itinerary. Members immediately see it and can
propose alternatives.
2 Member submits proposal. Proposal appears live to everyone.
3 Members vote. No requires a typed reason in
votes.comment; every reason is visible.
4 Admin invokes AI after a No. AI recommendation panel shows every
holdout suggestion.
5 AI attempts common ground. It blends compatible suggestions before
branching.
6 Admin presents candidate. Admin may repeat, accept, reject,
override or branch.
7 Trip Chat override. Unanimous agreement can terminate the
AI process immediately.
Mode NA — No-Admin
# Step Behaviour
1 Proposal added. No timer starts.
2 Members vote. No requires the member's own typed
suggestion.
3 No No exists. Plan carries forward; no repeating
background timer.
4 FIRST No arrives. 10-minute response window begins.
5 AI creates blended plan. One candidate; original remains visible.

Edge cases
Scenario Resolution
No without reason Blocked at UI/API level.
No one ever votes No No timer; plan carries forward.
New proposal during active round Queued for next decision cycle.
Multiple Yes votes by same member Only one active Yes; prior Yes is retracted.
Member silent during round Non-no; may still object later.
3rd unresolved common-ground round (NA) AI evaluates fixed requirements and branches automatically if
exhausted.
3rd unresolved round (Admin) AI recommends branching; admin decides.
3+ genuinely distinct holdouts 3+ branches, not binary.
Single-person branch Auto-resolves.
Branch disagrees internally Recursive consensus/branching.
Unanimous Trip Chat agreement mid-round Immediately overrides/terminates current AI process.
Low-confidence face match Unknown; never force-tagged.

6. Data Model Usage
Use the provided schema; extend additively
Provided table Use
trips Trip dates, destination, party, budget; group-trip flag.
trip_members Membership + role; owner is Mode-A admin.
itineraries Versioned plan; version used for optimistic concurrency;
generated_by records source.
itinerary_items One row per slot/activity; status + locked state.
proposals add/remove/replace/reschedule actions; closes_at holds the
10-minute window; status drives slot state.

users Traveller identity; locale.
user_preferences Interests, languages, pace, budget for compatibility.
tour_guides Language, specialisation, price, rating for guide matching.
cities/countries/currencies/languages Reference data and multilingual metadata.
New table Purpose
branches Recursive branch tree via parent_branch_id.
branch_members Member-to-branch assignments.

trip_chat_messages Mandatory always-on Trip Chat.

snake_case enums; BCP-47 language tags. The provided PS-11 dataset was checked with starter queries and
conformance tooling before finalising this design.

11. Language Approach — English Only
● Dataset language metadata remains available through languages, users.locale, city language and guide
language fields.
● React UI is English-only using a key-based string table; no translation service is required.
● Language is still used in guide matching and solo/group compatibility.
● User-generated chat and vote-reason text is displayed as typed; no live translation is built.
● XR device declaration: not applicable — WanderMatch has no AR/VR component.
Appendix. Business Benefits
● Fewer stalled trips: every disagreement has a concrete resolution path.
● No silent overrides: every No and reason is visible and preserved.
● Faster consensus: AI compresses negotiation into a candidate proposal per round.
● Branching avoids forced compromise when preferences are genuinely incompatible.
● Solo travellers get a real on-ramp into compatible groups or guides.
● Trip memories require little manual sorting through opt-in face-based grouping.
● Always-on Trip Chat keeps discussion and decision-making in one place.
